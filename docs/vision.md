# Техническое видение: telegram-webhook-bot-proxy

Сводный технический зафиксированный план: от [идеи проекта](idea.md) к минимальному рабочему решению для проверки гипотезы.

## Цель и границы

Сервис **изолирует** основное приложение от прямого взаимодействия с Telegram: исходящие сообщения уходят в Telegram только через этот прокси, входящие вебхуки от Telegram принимаются здесь и перенаправляются в основное приложение. Цель первой итерации — **подтвердить идею** с минимальными силами, без лишних функций и инфраструктуры.

**В границы MVP входят:** HTTP API прокси, приём вебхуков, пересылка запросов дальше, базовая конфигурация и логи. **Вне scope** на этапе проверки идеи: отказоустойчивый кластер, сложная очередь сообщений, аналитика, админ-интерфейс — пока не рассматриваются, если не понадобятся явно.

## 1. Технологии, зависимости и сборка

| Решение | Назначение |
|--------|------------|
| **Python 3.12+** | Единая целевая версия языка. |
| **uv** | Управление зависимостями и lock-файлом, создание venv, запуск: `uv sync`, `uv run`. |
| **FastAPI** | ASGI-приложение: приём вебхуков и HTTP API. |
| **async/await** | Единый стиль: и приложение, и HTTP-клиенты (без смешивания с синхронным кодом в бизнес-логике). |
| **httpx** (async) | Исходящие HTTP-запросы к Bot API Telegram и к основному приложению. |

- **Проект:** один корневой `pyproject.toml`, зависимости фиксируются lock-файлом `uv` (команды согласуются в `Makefile`).

- **Сборка / запуск без Docker:** через `uv` и цели `make` (установка зависимостей, локальный запуск приложения, при необходимости тесты).

- **Локальный запуск в Docker:** `Dockerfile` и при необходимости `docker-compose` только для **локальной** проверки; деплой на удалённый сервер в этом документе не детализируется.

- **Make:** единая точка входа для сценариев «с Docker» и «без Docker» (короткий набор целей без дублирования смысла `uv`).

Дополнительные библиотеки (валидация, тесты и т.д.) вводим по мере необходимости, с приоритетом стандартных и простых вариантов.

## 2. Принципы разработки

- **KISS** — только то, что нужно для проверки идеи; без «заделов на будущее» и лишних слоёв.
- **ООП** — ответственность разнесена по понятным объектам, логика не свалена в один монолитный скрипт.
- **Один публичный класс — один файл** (имя файла согласовано с классом). Исключения: точка входа приложения (`main` / `__main__`), пустые или минимальные `__init__.py`, при необходимости один небольшой модуль настроек без обязательной упаковки в класс.
- **Без оверинжиниринга** — никаких лишних паттернов, обёрток вокруг фреймворка и «универсальных» абстракций ради элегантности.
- **Тесты** — по мере необходимости, небольшой объём; критичный путь можно покрыть выборочно (инструмент — например, **pytest**, зафиксируем при появлении тестов в репозитории).

## 3. Структура проекта

**Плоская схема:** без `src/…/sublayers` и без глубокой иерархии пакетов. Код прокси — в одном пакете `app/`, все модули **на одном уровне** (один класс с осмысленной ответственностью — один файл). Новые модули добавляются по мере появления новых классов, не «папками заранее».

Корень репозитория (ориентир):

```text
.
├── app/                 # пакет приложения, плоский набор модулей
│   ├── __init__.py
│   ├── main.py          # точка входа (создание app, uvicorn)
│   └── ...              # остальные модули по мере реализации
├── tests/               # тесты, тоже без глубокой вложенности
├── docs/                # idea.md, vision.md
├── pyproject.toml
├── uv.lock
├── Makefile
├── Dockerfile
└── docker-compose.yaml  # при необходимости для локали
```

Инфраструктурные и служебные файлы — в **корне**; вложенные каталоги внутри `app/` на MVP не планируются, пока нет уважительной причины.

## 4. Архитектура

Три крупные части, без промежуточных «слоёв ради слоёв»:

1. **HTTP-граница (FastAPI)**  
   Маршруты: приём вебхука от Telegram, эндпоинт(ы) для **исходящих** вызовов от основного приложения к прокси (который затем бьёт в Bot API). Обработчики **тонкие**: валидация на минимальном уровне, сразу делегирование в клиенты. Создание `FastAPI` и связывание зависимостей — в `main.py` (точка входа).

2. **Клиент Telegram (Bot API)**  
   Один класс: async `httpx` к `https://api.telegram.org/…` (токен и методы в конфиге/настройках). Вся «работа с Telegram» в одном месте, чтобы не размазать URL и токен по коду.

3. **Клиент основного приложения**  
   Один класс: async `httpx` к **базовому URL** основного сервиса. При приходе вебхука от Telegram прокси **перенаправляет** запрос (тело, при необходимости заголовки) на заранее заданный путь/контракт. Детали пути кодируем в настройках, не в духе жёсткого DTO для всей модели Telegram — для проверки идеи достаточно **проксирования payload** (при ужесточении контракта — позже).

**Потоки:**

- *Основное приложение → прокси → Telegram:* вызов API прокси → клиент Bot API.  
- *Telegram → прокси → основное приложение:* вебхук на прокси → клиент основного приложения (forward).

**Обработка ошибок (MVP):** логирование, понятные HTTP-коды наружу, без ретраев с бэк-оффом и без очередей, пока не появилась реальная потребность.

Очереди, БД, шина событий, отдельный **domain layer** вводятся только если MVP перестаёт укладываться в сценарии; до этого **не** закладываем.

## 5. Модель данных

**Персистентного хранилища в MVP нет** — никакой БД и файлового журнала состояния. Всё, что «настроечное», живёт в **конфигурации** (см. раздел про настройки): базовый URL основного приложения, путь вебхука, публичный URL/порт сервиса, таймауты `httpx` — по необходимости.

**Секреты** (токен бота Telegram, при необходимости ключ/заголовок для вызовов к основному приложению) — только **из переменных окружения** или аналогичного механизма при деплое; в репозиторий не коммитить.

**В памяти** остаётся лишь то, что создают клиенты и приложение при старте (сессии `httpx`, экземпляр FastAPI). Сущностей вроде «пользователь», «очередь сообщений» в схеме данных **нет**; payload Telegram и тело запросов — это «сквозной» JSON/bytes через прокси, не отдельная доменная модель на первом этапе.

## 6. Сценарии работы

**С1. Исходящее сообщение (основное приложение → прокси → Telegram)**

1. Основное приложение вызывает **HTTP API прокси** (метод, тело, заголовки — в рамках согласованного минимального контракта, без усложнения).  
2. Прокси по настройкам и секрету вызывает **Bot API Telegram** (например, `sendMessage` или другое подходящее действие).  
3. Прокси возвращает основному приложению ответ Telegram (успех или ошибка), при необходимости с минимальной нормализацией кода.  
4. Ошибки сети/таймаута/HTTP от Telegram: фиксация в лог, клиенту основного приложения — неуспех с понятным статусом (без повторных автоматических попыток в MVP).

**С2. Входящий вебхук (Telegram → прокси → основное приложение)**

1. Telegram доставляет обновление на **URL вебхука**, настроенный на этот прокси.  
2. Прокси принимает тело (как приходит, без лишнего маппинга на DTO) и **перенаправляет** запрос к основному приложению (путь/метод из конфига, заголовки — по соглашению с интеграцией).  
3. Успех: прокси отдаёт вызывающему (Telegram) ответ, согласованный с интеграцией (часто — как вернул основной сервис, либо короткое 2xx).  
4. Сбой основного приложения или сети: **лог**, коду ответа для Telegram **фиксировать в интеграции** (например 2xx vs 5xx), без очередей и гарантированной доставки в MVP.

**С3. Старт и локальная проверка**

1. Поднять прокси через `make` (без Docker) или `make` + Docker, задать env.  
2. Проверить, что health/корневой маршрут (если есть) отвечает, при необходимости прогнать тестовый вебхук `curl`ом и сценарий исходящего вызова.

Сценарии **сохраняют порядок и границы** из [идеи](idea.md); углубление контракта (точные пути, схемы JSON) — при реализации, без фиксации в этом документе сверх необходимого.

## 7. Конфигурация

**Источник правды — переменные окружения.** Отдельных тяжёлых YAML/JSON-файлов, удалённого конфиг-сервера и профилей «local/stage/prod» в репозитории нет: минимум сущностей, один понятный способ задать значения (env в Docker, в `make`, в оболочке).

**Код:** один небольшой модуль (например, `config.py` или `settings.py`) читает env **при старте**, собирает в одну структуру (класс настроек или `NamedTuple`/датакласс — без фанатизма). Удобно — **pydantic-settings** (`BaseSettings`) для валидации и типов; если захочется ещё проще — ручной разбор, но тогда внимательнее к опечаткам в имёнах переменных.

**Секреты** — только через env (согласовано с разделом «Модель данных»); **не** храним в исходниках. В репозиторий допустим **`.env.example`**: пустые/фиктивные значения и комментарии, без реальных токенов. Локально при необходимости — `.env` в `.gitignore` и подхват при разработке (если выберем библиотеку, которая читает `.env`).

**Ориентир имён (уточняются в коде):** хост/порт bind ASGI, базовый URL и путь(и) к основному приложению, таймауты `httpx`, уровень логирования, при необходимости bearer к API основного приложения — что реально используем, то и вводим, без «всех возможных» переменных заранее. Проверка `X-Telegram-Bot-Api-Secret-Token` при необходимости выполняется **в основном приложении**, прокси только пересылает заголовок.

## 8. Логирование

**Модуль `logging` стандартной библиотеки** — без отдельного «лог-стека» (ELK, sidecar и т.д.) на этапе проверки идеи. Настройка **один раз** при старте из настроек: уровень (например `INFO` / `DEBUG`) из env, единый формат сообщения (время, уровень, имя логгера, текст), вывод **в stdout** — чтобы Docker и `journalctl` забирали сами.

**Содержание:** старт/остановка, входящий маршрут/метод (без сырого body целиком в `DEBUG` без необходимости), **ошибки** клиентов `httpx` (код, URL **без query с токеном**), длительность тяжёлых шагов — только если понадобится, не меряем «всё заранее».

**Нельзя в лог:** токен бота, `Authorization` и иные секреты, полные query-строки к Bot API, если в них есть `token=`. Тела запросов/ответов — **не** логируем в полном виде в прод-режиме; при отладке — осознанно и с маскировкой, либо фрагменты. Структурированные JSON-логи (одна строка на JSON) **не** обязательны для MVP, достаточно читаемой строки.

## 9. Сборка и деплой

**Сборка артефакта** — это **установка зависимостей** в изолированное окружение по `pyproject.toml` и lock-файлу: `uv sync` (или `uv lock` при изменении зависимостей). Отдельной «компиляции» бинаря нет; приложение запускается как **модуль Python** / через `uv run` (конкретная команда — в `Makefile`).

**Локально без Docker:** цели `make` вызывают `uv` (синхронизация, запуск ASGI-сервера, при появлении тестов — `pytest`). Имена целей держим короткими: например `install`, `run`, `test` — без дублирования длинных команд в документации.

**Локально с Docker:** один **Dockerfile** (базовый образ с Python 3.12+, копирование проекта, `uv sync --frozen` или эквивалент, `CMD` с запуском приложения). При необходимости **docker-compose** — порт, env-файл или переменные, **без** обязательного стека из БД и прочих сервисов. Цели `make` для `docker build` / `docker compose up` — единая точка входа рядом с «без Docker».

**Деплой на удалённый сервер** в рамках этого документа **не детализируется**: при появлении хостинга достаточно образа или `uv run` на ВМ/в PaaS с теми же env. CI/CD, канареечные выкаты, оркестраторы — **вне** MVP, пока не понадобятся явно.
