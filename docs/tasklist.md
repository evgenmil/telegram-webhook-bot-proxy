## Итерации (чек-лист)

### Итерация 1 — Каркас и «живой» сервис

Появляется поднимаемый HTTP-сервис с минимальным ответом (например health / корень), по которому видно, что процесс рабочий.

- [x] Репозиторий: зависимости, точка входа, запуск одной командой
- [x] Маршрут проверки доступности (health или аналог)
- [x] Ручная проверка: запрос к сервису, ожидаемый ответ

### Итерация 2 — Конфигурация из окружения

Сервис читает нужные для дальнейших шагов параметры из переменных окружения, при старте валидирует обязательное.

- [x] Модуль настроек: чтение env при старте
- [x] Список обязательных и опциональных переменных согласован с планом интеграции
- [x] Ручная проверка: успешный старт с полным набором env, понятная ошибка без обязательных
- [x] Пример для разработчика: `.env.example` без реальных секретов

### Итерация 3 — Исходящий сценарий: приложение → прокси → Telegram

Основное приложение обращается к API прокси; прокси вызывает Bot API Telegram и возвращает результат вызывающему.

- [x] HTTP-эндпоинт прокси по согласованному минимальному контракту
- [x] Вызов Telegram Bot API из одного места (токен не размазан по коду)
- [x] Ручная/интеграционная проверка: через прокси уходит реальное действие бота (например тестовое сообщение), ответ доносится до клиента

### Итерация 4 — Входящий сценарий: Telegram → прокси → основное приложение

Прокси принимает вебхук от Telegram и пересылает тело (payload) в основное приложение по настройкам.

- [x] Маршрут вебхука на прокси
- [x] Пересылка на базовый URL и путь основного приложения (как в конфиге)
- [x] Ручная проверка: имитация вебхука (например `curl`) и/или доставка от Telegram; основное приложение (или его заглушка) получает ожидаемое тело; ответ цепочки согласован

### Итерация 5 — Ошибки, таймауты, логи (MVP)

Поведение при сбоях сети и ответов Telegram/основного приложения предсказуемо снаружи; в логах нет токенов и полного сырья секретов.

- [x] Понятные HTTP-коды и сообщения об ошибке для исходящего и входящего путей
- [x] Таймауты исходящих HTTP-вызовов из настроек
- [x] Логирование старта, маршрутов, ошибок — без утечки секретов
- [x] Ручная проверка: сценарий «основной сервис недоступен» / «ошибка Telegram» — ожидаемое поведение и чистые логи

### Итерация 6 — Локальный запуск: `make` и при необходимости Docker

Один понятный способ развернуть окружение у разработчика, как в [vision](vision.md) (С3).

- [x] Цели `Makefile`: установка, запуск, при появлении — тесты
- [x] При необходимости: `Dockerfile` и/или `docker-compose` для локали
- [x] Ручная проверка: чистая машина / коллега поднимает сервис по инструкции из короткого набора шагов

### Итерация 7 — Исходящие: прозрачный Bot API без хранения `api_key` в прокси

Сервис **не** хранит токен бота. Исходящие к Telegram — по той же схеме путей, что и `https://api.telegram.org` (`/bot<token>/<method>`), чтобы в клиенте (например `TelegramBot\Api` / PHP) можно было **подменить только хост** на URL прокси.

- [x] Проксирование запросов к `api.telegram.org` с тем же `path`/`query`/`body`, что у клиента
- [x] Удаление обязательного `TELEGRAM_BOT_TOKEN` из конфига и JSON-эндпоинта `POST /v1/outgoing/telegram`
- [x] Логи маршрутов: маскирование первого сегмента `bot<token>` / без секретов
- [x] Маршрут вебхука объявлён **до** `/{bot}/…`, чтобы `POST` на путь вебхука не уходил в forward
- [x] Проверка: ручной запрос `GET/POST` к `…/bot<токен>/getMe` (или `sendMessage`), сравнение с прямым вызовом Bot API; README/`.env.example` обновлены

### Итерация 8 — Вебхуки нескольких ботов: проброс хвоста пути

Один прокси принимает вебхуки нескольких ботов: у каждого свой URL `PROXY_INCOMING_WEBHOOK_PATH/<хвост>` (например id бота), хвост пробрасывается в основное приложение без интерпретации. Новых env нет.

- [x] Маршрут `PROXY_INCOMING_WEBHOOK_PATH/{suffix:path}` (до `/{bot}/…`); старый путь без хвоста работает как раньше
- [x] Пересылка на `MAIN_APP_INCOMING_PATH/<хвост>`; сегменты `.`/`..` → 404
- [x] Тесты (`tests/test_webhook_suffix.py`), README и `.env.example` обновлены

### Итерация 9 — OpenRouter-прокси и секрет доступа (EU egress)

Основное приложение не может напрямую ходить в OpenRouter; прокси размещён в ЕС и расширяется до egress-прокси: `/openrouter/<path>` → `https://openrouter.ai/<path>`. Ключ OpenRouter передаёт клиент в `Authorization`, прокси его не хранит. Чтобы прокси не был открытым, добавлен опциональный общий секрет.

- [x] `OpenRouterForwarder` + маршрут `/openrouter/{path:path}` (до `/{bot}/…`), стриминг ответа (SSE), `OPENROUTER_READ_TIMEOUT`
- [x] Ошибки сети/таймаута → `502`/`504`, сегменты `.`/`..` → 404
- [x] `PROXY_ACCESS_TOKEN`: при заданном значении исходящие маршруты требуют `X-Proxy-Access-Token` (иначе 401), заголовок в upstream не уходит
- [x] Тесты (`tests/test_openrouter_forward.py`, `tests/test_proxy_access.py`); vision, conventions, README и `.env.example` обновлены
